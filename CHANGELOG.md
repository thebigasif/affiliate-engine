## [v0.5.0] — 2026-10-03

### Added
- **`screen-backfill` screens commissions older releases never screened.** Sales credited before `commissions.screened_at` were only screened when the provider delivered the event again, which for most sales never happens. `affiliate-engine screen-backfill [-dry-run] [-limit N] [-since YYYY-MM-DD] [-json]` screens every commission credited from a sale that is pending or approved, has never been screened and has no hold (open or resolved), the same ones a replay would repair. Each is screened in its own transaction with the same rules and holds as a new sale, evaluated as of now. It is safe while the server runs, on SQLite and Postgres. It prints how many were scanned, screened and held (per rule, and each held commission) and the errors; a failed commission stays unscreened and the next run retries it, and a second run does nothing. `-dry-run` reports what would be held and writes nothing. `AE_FRAUD_DRYRUN=1` records verdicts and holds nothing, as for a new sale.
  - It does not run by itself on start. Every commission credited before the upgrade counts as never screened, including the ones the old release did screen, and the rules read data that arrived after the sale: on the demo data a pass holds 48 of 660 commissions that passed at the time. The operator runs the dry run and decides (DEPLOY.md, "Screening commissions from older releases").

### Changed
- **Ledger accounts are per currency.** `HOLD:<CCY>`, `EXPENSE:COMMISSION:<CCY>`, `PAYOUT_CLEARING:<CCY>` and `AFFILIATE_PAYABLE:<id>:<CCY>`, with the currency in `ledger_accounts.currency`. The ledger creates them on first use; nothing is seeded and affiliates no longer get an account when they are created. A journal moves one currency: `Post` refuses lines in two currencies (`ledger.ErrMixedCurrency`), and so does the database guard on both engines. Commission and payout currencies are upper-case, `""` is booked as USD, and a currency can no longer be changed once written.
  - **Migration (`percurrency_*.sql`, both engines).** On first start, every line on a legacy account (`HOLD`, `AFFILIATE_PAYABLE:42`, ...) moves to the per-currency account of its journal's currency, in one transaction, and the emptied legacy accounts are removed. Amounts, journals and ids are kept. The currency comes from the journal's commission, payout or raw event. A journal none of those attributes is put in the install's only currency; if the install has booked several currencies, the upgrade stops, names the journals, and changes nothing. An install that booked one currency gets it as the program currency. Re-runs do nothing. One `audit_log` row records the move.
  - Code that embeds the engine: `payouts.LedgerPoster` takes the payout's currency (`func(ctx, payoutID, affiliateID int64, currency string, amount int64) error`); `payouts.SettleLines` builds its lines. Account codes come from `ledger.Hold`, `ledger.Expense`, `ledger.Clearing` and `ledger.Payable`; `EnsureAccounts` only takes per-currency codes.
- **Program currency.** `program_settings.currency` (default USD) is what a commission rule, coupon or bonus tier without its own currency is in, and what `min_payout_cents` is in. `GET`/`PUT /api/v1/admin/settings` read and set it as `currency`.
- **Fixed rates and bonus tiers have a currency.** `commission_rules`, `coupons` and `rate_tiers` gain `currency` (empty = the program currency); the rules, tiers and partner-rate endpoints accept and return it. A fixed rule or coupon in another currency than the sale's is skipped and the next rule down applies (a yen sale past a "fixed $5" partner rate earns the program's percent rate). If no rule is left, the sale earns nothing and is recorded as `currency_mismatch`. Tier volume counts sales in the tier's currency only, and only sales in that currency use the tier. Nothing is converted between currencies.
- **Daily totals are per currency.** `daily_agg` and `token_stats_daily` have a `currency` in their key. A sale's count and commission go in the row of its currency. Clicks have no currency and stay in the `''` row, so the click path writes what it always did. The schema refuses money in a row without a currency.
  - **Migration (`aggcurrency_*.sql`, both engines).** On first start the two tables are rebuilt in one transaction. Clicks move to the `''` rows. A partner whose sales were all in one currency keeps its rows and days, in that currency. A partner with sales in several currencies gets its money rebuilt from its commission rows, one row per currency and per day the commission was recorded. Money with no commission behind it goes to the program currency. Totals are kept. Re-runs do nothing.
  - The reconciler heals clicks in the `''` rows only. `analytics.Reconciler.Dashboard` returns `DashboardTotals` with commission per currency.
  - `GET /api/v1/affiliate/stats/drill` rows add `currency` and `commissions` (per currency); `commission_cents` is the program currency's. `TokenStats.Drill` takes the currency, and `ApplyConversion` takes the conversion's currency. A rollup no longer wipes a day's conversions.
  - `export-parquet`: `daily_agg.parquet` has a `currency` column. Sum `commission_cents` per currency.
- **MLM volume is in the program currency.** Business volume (`mlm_volume_daily`) counts commissions in the program currency only, like bonus tier volume: a yen sale in a dollar program adds no volume, and nothing is converted. Tier splits are in the currency of the commission they split: `mlm_period_lines.currency` (filled in from the commission on upgrade), and `mlm.Engine.PeriodTotal` returns totals per currency.
  - Code that embeds the engine: `commissions.Engine.MLMBV` and `mlm.Engine.RecordBV` take the commission's currency (`func(ctx, affiliateID, day int64, currency string, bv int64) error`).
- **Minimum payout per currency.** `min_payout_by_currency` in the settings (`{"JPY": 5000}`, minor units of each currency) sets the minimum for other currencies; a currency without one uses `min_payout_cents` as before. Payout runs use them (`payouts.Thresholds`, `CreateBatchWith`, `PreviewWith`); an explicit `min_threshold_cents` on a run still applies to every currency. Dry-run batches carry a formatted `display` amount.
- **Totals are per currency, never added up.** The single-number fields keep their names and report one currency (the program currency, or the one the partner or program has money in). Added alongside them:
  - `GET /api/v1/affiliate/earnings`: `currency` and `currencies` (per currency: totals, payable balance, unpaid, earned, owed and the ledger proof). `ledger_proof.holds` is true only when every currency holds.
  - `GET /api/v1/affiliate/ledger`: `?currency=`, `currency` and `currencies`.
  - `GET /api/v1/admin/dashboard`: `currency`, `commissions_by_currency`, `payouts_paid_by_currency`, `ledger_integrity_by_currency`, and `earned` per top affiliate. `ledger_integrity_sum` is 0 only when every currency balances.
  - `GET /api/v1/admin/affiliates`: `currencies` per partner and the list's `currency`.
  - The daily chart's commission is the program currency's. Each day also lists `commissions`, one entry per currency.
  - The digest, the MCP tools, the Monday report and the partner recap list money per currency, formatted for each currency (`5,000 JPY`, `$12.50`). The Monday report ranks top partners by sales. Doctor checks the ledger and the payable proof per currency. Gamify milestones count the program currency.
  - The dashboard and portal show every currency where they show totals, and money typed into Settings is in the program currency (yen has no cents).
  - The partner's ledger page has a Currency picker when they have money in more than one currency. Each currency is its own balance. The Last 30 days chart on the Overview and the partner's Earnings page has one too, for commission.
  - The live demo's portal shows the top earner in the program currency.

### Fixed
- **Cloud: Stripe webhooks connected before v0.4.0 never got dispute events.** Connect Stripe subscribes a new webhook to the events the engine reads, but an existing one kept the list it was made with, so `charge.dispute.funds_withdrawn` and `charge.dispute.funds_reinstated` only reached workspaces that reconnected. The control plane now adds missing events to every connected Stripe webhook, once per version of the event list, shortly after start and every 15 minutes, with the workspace's own key. It only adds: events the owner added stay, and nothing is removed. Failures are retried with backoff (5 minutes up to 12 hours). If the key can't do it (revoked, no Webhook Endpoints: Write, endpoint deleted), the Stripe card in Settings asks the owner to reconnect. Control db migration step 2 adds the `webhook_sync` table.
- **Clicks were lost on every shutdown and restart.** The click writer runs on the engine's signal context. On SIGTERM it wrote only the batch in hand, with the already-cancelled context, so that write failed too; clicks waiting in the buffer, and redirects that finished during the 5-second graceful shutdown, were never written. Those visitors' attribution rows were missing, so a later sale through that link could go unattributed. The writer now stops intake, waits for redirects already handing over a click, and writes everything accepted with a context of its own (10 seconds at most). Clicks arriving after that are refused, not stranded. Anything waiting on a click (the bench, the demo seed) no longer hangs.
- **A refund in one currency could fail a payout in another, after the money was sent.** A partner's balances in all currencies were one account. A ¥20,000 refund after a yen payout plus $100.00 owed made one balance of +10000: the $100.00 payout was planned, the rail sent it, and the settle then hit the overdraft guard and the payout went to `failed`. Balances, the overdraft guard, settles, clawbacks and payout netting are now per currency.
- **Yen sales crossed dollar bonus tiers about 100 times early.** Tier volume added yen to cents. It is counted per currency now.
- **A fixed rate paid the same number in any currency.** "Fixed 500" paid $5.00 on a dollar sale and ¥500 on a yen sale. It pays only sales in its own currency now.
- **Summaries added currencies together and printed the sum in dollars** (digest, MCP, dashboard, emails). See Changed.
- **A sale the fraud rules flagged could be paid.** Webhook sales were screened after the credit committed, and the fraud hold was a separate write. If the server stopped in between, or the hold write failed, the commission stayed unheld, matured and went into the next payout. A failed hold write was only logged, and the webhook still answered 200. The rules, their verdicts and the hold now run in the credit's own transaction: they commit with the journal and the commission, or the credit rolls back and the webhook fails so the provider retries. A rule that errors still holds the sale as `screening_error`. Shadow mode (`AE_FRAUD_DRYRUN=1`) records verdicts and holds nothing, as before. The 5-minute sweep is unchanged.
  - Sales credited by earlier versions and never screened are screened when the provider delivers the event again. Each commission is screened once: a new column, `commissions.screened_at`, records it. A sale that already has a hold, open or resolved, is left as it is. If that screening cannot write its hold, the replay fails and the provider retries.
  - Code that embeds the engine: `commissions.Engine` gains `ProcessPurchaseScreened` and `ScreenCommission`. `fraud.WithTx` runs the fraud engine inside a transaction, and custom rules read through `fraud.Conn`.

### Security
- **Cloud: signups confirm their email.** Anyone could sign up with any address: unlimited trials with throwaway emails, and an account squatted under someone else's address could invite its own teammates, who stayed after the real owner took the account back with a password reset. With email on, a signup now starts unverified, gets no session, and is emailed a confirmation link (32 random bytes, stored hashed, single use, 24 hours, only the newest works; `GET /verify` shows a button, `POST /verify` confirms, signs in and opens checkout). Until confirmed, the owner can sign in and look around but can't start checkout or a trial, invite, turn on two-step sign-in, or connect billing or a domain. "Send the link again" is limited to 3 an hour. A password reset confirms the email too; on an unconfirmed account it also removes teammates, invites and two-step sign-in in the same transaction (and replaces the API keys if a teammate had joined), and the account page says so. Control migration step 4 adds `accounts.email_verified` (existing accounts are marked confirmed) and `email_verifications`. Owner grants and signups while email is off start confirmed.
- **Cloud: signup no longer tells who has an account.** With email on, "That email already has an account" is gone: an email that has a login gets the same "Check your email" page as a new signup, and the address gets a note ("someone tried to sign up with your email; sign in or reset"), 2 an hour at most. A taken workspace address is now checked before the email, so "That address is taken" can't be used to probe emails either.
- **Cloud: partner email goes through a relay with quotas.** Any workspace, even on a trial, could add partners with any address and send them 5,000-character news emails from the cloud's verified address under any sender name. Engines held the provider key itself. They now get a token of their own and send through the control plane's relay (`127.0.0.1:CLOUD_PORT_BASE`, Postmark's API), which holds the key and enforces, per workspace and UTC day, `CLOUD_MAIL_DAILY_TRIAL` (100) on a trial and `CLOUD_MAIL_DAILY_PAID` (2,000) otherwise; program news only on a paid or comped plan or once the account is `CLOUD_MAIL_NEWS_AFTER_DAYS` (7) old; no sender names that imitate well-known brands or read like an account alert ("security", "billing", "verify", "password", "support team"; whole words, case-insensitive); and nothing for paused accounts. From is always the cloud's address and Reply-To the account owner. Control migration step 5 adds `mail_sends`. Engines restart once on upgrade to pick up the new settings.
- **Cloud: the two-step lockout survives a restart.** The wrong-code budget (10 wrong codes an hour per login) was kept in memory, so restarting the control plane gave a guesser a fresh 10. It is in the control database now (control migration step 3, `code_failures`), with the same rules: every try counts before it is checked, a right code gives its count back.

## [v0.4.0] — 2026-10-03

### Added
- **Off-box backups (Cloud).** With `CLOUD_BACKUP_S3_*` set, the nightly backup is also copied to Cloudflare R2 or any S3-compatible store.
  - The control database is now backed up too, locally (`/data/backups/control/`, newest 7) and off the box.
  - Uploaded: the control database, each workspace database and each workspace's attribution secret, then a `manifest.json` with sizes and SHA-256s. The sealing key is never uploaded; CLOUD.md says how to escrow it.
  - Everything uploaded is encrypted (AES-256-GCM in 64 KiB chunks, key from `CLOUD_BACKUP_PASSPHRASE` through PBKDF2 and HKDF). Turning off-box backups on without a passphrase of 16 characters or more stops the app from starting.
  - Objects older than `CLOUD_BACKUP_REMOTE_DAYS` (30) are deleted, only after a fully good upload.
  - Requests are signed with AWS Signature Version 4 by a small built-in client. No new dependency.
- **Backup health (Cloud).** `GET /healthz/backups` returns JSON with the age of the last good local and off-box backup. It answers 503 once either is older than `CLOUD_BACKUP_STALE_HOURS` (36), for an uptime monitor. `/healthz` is unchanged. A failed run logs `cloud: BACKUP FAILED` and is recorded.
- **Restore tools (Cloud).**
  - `cloud backup` backs up now. `cloud backups` shows the last results and the sets in the bucket.
  - `cloud restore-check` downloads the newest set, checks it against the manifest, decrypts it, opens the control database, checks every database's integrity and ledger, and checks the sealing key.
  - `cloud backup-fetch -out DIR` lays a set out like `/data`. `cloud backup-decrypt` decrypts one file.
  - CLOUD.md has the restore runbook.
- **Control database migrations (Cloud).** `cloud.db` now upgrades itself through numbered steps, recorded in a `schema_migrations` table. Each step runs in one transaction, and steps already applied are skipped. Step 1 accepts every control database an earlier build wrote and checks each table's columns. A control database from a newer build is refused with a clear message instead of being opened. Before this, the first schema change would have stopped the Cloud from starting.
- **Polar.** Sales from Polar are credited through its webhook (`/webhooks/polar`, `AE_POLAR_SECRET`).
  - The signature is checked with Standard Webhooks, and Polar's earlier signing key is accepted too.
  - A paid order credits its net amount (after discounts, before tax), renewals included. `order.refunded` claws back the refunded share. A $0 order binds the customer for renewals.
  - The tracking script adds the partner's token to Polar checkout links as `reference_id`.
  - Cloud Settings has a Polar field.
- **Teammates (Cloud).** The owner invites people by email. Each teammate joins with their own password and can open dashboards and see settings, but not change billing, the team, new workspaces, settings, billing connections, the domain or API keys. Removing a teammate signs them out at once and replaces the API keys. Up to 10 per account.
- **Two-step sign-in (Cloud).** Codes come from any authenticator app: a QR code to scan, a key to type, and 10 one-time recovery codes. Each code signs in once, five wrong codes end the attempt, and 10 wrong codes in an hour pause code entry for that login. A password reset still asks for the code. Turning it off needs the password and a code. It works for the owner and for teammates.
- **A special rate for one partner.** Set in the partner panel (`PUT /api/v1/admin/affiliates/{id}/rate`). It applies to their new sales and comes before bonus tiers. The partner's portal shows it as their deal.
- **Bonus tiers screen.** Settings, Bonus tiers lists, adds and removes the program's volume tiers. The portal tells partners the next tier and how far they are from it (`deal` in `GET /api/v1/affiliate/earnings`).
- **Test your setup.** A guided check with three live steps:
  - the tracking script on the owner's site, fetched with the SSRF-guarded client;
  - a click through a test partner's link (`setup-test`);
  - a test-mode sale credited to that partner.
  - Routes: `POST /api/v1/admin/setup-check/site`, `POST /api/v1/admin/setup-check/start`, `GET /api/v1/admin/setup-check`.
- **Partner resources.** Owners add banners and logos (PNG, JPEG, WebP or GIF, up to 2 MB), text to copy (`{link}` becomes the partner's referral link) and links to pages. Partners find them under Resources in their portal, with copy buttons and embed code. Images are public, so partners can show banners on their own sites.
- **Reject with a reason.** Rejecting an application can include a reason. With email on, the applicant gets a short, polite note.
- **Regular program emails.** Each one can be switched off in Settings, Emails:
  - **A Monday report for the owner:** last week's clicks, sales and commission next to the week before, and the top three partners. It sends from 08:00 UTC on Monday, and a missed week is skipped after Wednesday.
  - **Tips for partners who haven't started:** an active partner 7 to 30 days in whose link has no clicks gets their link, three ways to share it, and their deal. It goes once, and not at all if they get a click before it sends.
  - **A monthly recap for partners:** from 08:00 UTC on the 1st, each active partner with clicks or earnings last month, or money waiting, gets that month's clicks, sales and earnings, plus what's ready to pay and what's in hold. It nudges partners without payout details.
  - Partner emails use the program-news unsubscribe. The unsubscribe page now reads "Stop program emails", covering news, tips and recaps.
  - New tables: `program_emails` for the switches and `email_log` so each email goes once per period. GDPR erase removes a partner's rows.
  - The Settings panel "Notifications" is now "Emails", with "To you" and "To your partners" sections.
- **Partners are asked where to be paid.** When a payout waits for a partner who hasn't added payout details, the engine emails them a sign-in link that opens "How you get paid".
  - It sends right after a payout run, and a half-hourly check catches the rest.
  - A partner is asked at most once a week, and never after they've added details.
  - The dashboard shows who hasn't said: "No payout details" in the partner list, and "Not given yet", with the date we emailed them, in the payout list and the partner panel.
  - The portal puts "How you get paid" first until it's filled in.
  - The demo's partners have sample payout details.
  - New table: `payout_details_asks`. GDPR erase removes it.
- **Where partners get paid.** Partners add their PayPal email, Wise email or bank details under "How you get paid" in their portal (`GET`/`PUT /api/v1/affiliate/payout-details`).
  - The details are sealed at rest with AES-256-GCM, bound to the affiliate. The key is derived from the deployment secret, domain-separated from the tax-form key.
  - The owner sees "Pay to" in the payout list, in the partner panel and in the Mark as paid confirmation.
  - The PayPal and Wise CSV exports pay the partner's address for that rail, falling back to their login email.
  - GDPR erase removes the details.
- **A heads-up when something needs you.** The engine emails the program owner when applications, held commissions, payouts to send or tax forms to review are waiting.
  - At most one email a day, and only when something new arrived since the last one.
  - Settings, Notifications turns it on or off and sets the address. It defaults to `AE_OWNER_EMAIL`, which is the account email on Cloud. Without it, the default is `AE_MAIL_REPLY_TO`.
  - It needs partner email to be on (`AE_MAIL_*`).
- **Partners see their payouts.** The partner's Earnings page has a "Your payouts" list: date, amount, how it was sent, and Paid or On its way. New route: `GET /api/v1/affiliate/payouts`, the affiliate's own payouts, newest first, without failed ones.
- **Accessibility everywhere.** axe-core now reports no violations on any dashboard page (desktop and phone), on all 47 website pages, or on the cloud sign-up, sign-in, account and settings pages. The fixes:
  - The faint greys, the "yes" green, and the coral and blue pills are darker, for 4.5:1 contrast.
  - The phone top bar is a header landmark.
  - Code boxes that scroll can be reached with the keyboard.
- **Demo links open the right page.** In the demo, a link straight to a partner page (like `#/home`) now opens that page with its data, instead of an empty page.

### Changed
- **Approving a paid payout is a no-op 200** (`"already_paid": true`) instead of a 409, so a double click or a retried request is safe. The check runs under the payout lock; no rail runs and no journal posts.
- **`net_terms_days: 0` now means no hold.** It was silently treated as 30 on the purchase and usage paths, and `POST /admin/campaigns` rewrote an explicit 0 to 30.

### Fixed
- **Money moves were not atomic.** A purchase credit, refund, maturation, fraud uphold, payout settle or usage settlement posted its ledger journal in one transaction and wrote the commission, clawback, payout, outbox and processed rows in another. A failure between them left a journal with no commission, or a status change with no journal, and the repair was a reversing journal whose error was ignored. The journal and its rows now commit in one transaction on the ledger connection (`ledger.Poster.Run`), or nothing does. The reversing journals are gone: a failed attempt leaves nothing behind and the retry starts clean. Idempotency keys are unchanged, and journals left half-done by earlier versions are still finished on the next delivery.
  - Code that embeds the engine: `commissions.Poster`, `fraud.Poster`, `httpapi.Poster` and `usage.Poster` gain `Run`, and `payouts.Ledger` must be set to the same poster as `payouts.LedgerPoster` (main does both).
- **Two servers on one Postgres could move the same money twice.** Refunds, maturation, fraud upholds and payouts were kept apart by a lock inside each process only. A maturation on one server and a refund on the other could both move a commission's money: HOLD over-drained and the partner was owed the full commission after half of it was refunded. Each money transaction now locks the commission, payout or usage meter row it decides on (`SELECT ... FOR UPDATE`), and paying out locks the partner's payable balance, so servers wait for each other in the database. An uphold of a commission whose payout another server is executing is refused until it settles (409). SQLite is unchanged: its write lock already covers this.
- **PayPal and Wise payout files paid yen and dinar wrong.** Every amount was written with two decimals, so a ¥5,000 payout went out as ¥50.00 and a 1.000 KWD payout as 10.00. Amounts now follow each currency's ISO 4217 decimals (none for JPY and KRW, three for KWD and BHD). Partner emails and the dashboard show them the same way. The rules live in one place, `internal/money`.
- **Frozen or removed partners still earned through a coupon or a past customer.** When the attribution check found nobody active, the engine's own coupon and customer lookup credited the partner anyway (the fraud rule then held it). That lookup now requires an active partner, like the attribution check, and credits a returning customer in the program they signed up in.
- **Coupon and returning-customer sales were missing from the dashboard's per-partner totals.** They were counted under partner 0. They now count under the partner who earned them.
- **A Stripe Connect transfer that timed out could be paid twice.** If Stripe made the transfer but the response was lost, and a refund then made the payout re-batch, the next run sent the money again. A payout handed to a real rail is now marked (`payouts.rail_attempted_at`), and before re-batching it the runner asks the rail whether the transfer landed (`Runner.RailLookup`). If it did, the payout is settled as paid and flagged for the operator. If the rail can't say, it is flagged and nothing is re-batched.
- **Stripe Connect could mark a payout paid with nothing sent.** Transfer groups and idempotency keys were `ae_payout_<id>`, so after a database reset, or with staging on the same Stripe key, a new payout could adopt an old transfer. They now carry an id minted once per install (`install_identity`), and a transfer is adopted only if it pays this payout's destination, amount and currency and is not older than the payout. Transfers made under the old group name before upgrading are still found, with the same checks.
- **Usage settlement could leave money in hold with no commission.** If saving the commission failed and more usage arrived before the retry, the retry posted the whole amount again under a new key, and the first journal stayed in hold. The retry now finishes the journal it already posted, and the next run settles the rest.
- **Stripe: a second partial refund took back too much.** Stripe's refund webhook only says how much has been refunded in total so far, and that total was treated as the new refund's own amount. Two $30 refunds on a $100 sale took back 90% of the commission instead of 60%. Refunds now take back only what earlier refunds have not, and an old delivery that arrives late takes nothing.
- **Stripe: chargebacks kept the commission.** `charge.dispute.funds_withdrawn` now takes back the disputed share like a refund, once per dispute. `charge.dispute.funds_reinstated` (you won) is logged, and the commission stays taken back: add it again by hand if the partner should keep it. Cloud adds both events to new Stripe connections; reconnect Stripe to add them to an existing one.
- **Stripe: refunds of subscription invoices were missed on webhook API version 2025-03-31 and later.** That version took the payment id off invoices and the invoice id off charges, so a refund could not find the commission. The engine reads the invoice's `payments` list, and the new `invoice_payment.paid` event links an invoice to its payment in either order. Add `invoice_payment.paid` to your webhook if it uses that version.
- **Stripe: a one-time Checkout with "create invoice" turned on paid the partner twice.** Stripe sends both `checkout.session.completed` and `invoice.paid` for the same payment. Whichever arrives first now earns the commission and the other is skipped.
- **Commission was paid on tax for Chargebee, Recurly, Lemon Squeezy and Stripe one-time Checkout.** They now pay on the amount after discounts and before tax (`total - tax`), like Stripe invoices, Paddle and Polar. Refunds there include tax, so they are measured against the total the buyer paid, tax included: half the money back still takes back half the commission.
- **A refund could fail to find its commission for good.** After crediting a sale, the engine saves the ids a later refund looks for; with Stripe, Paddle, Chargebee, Recurly, Lemon Squeezy and Polar a failed save was ignored. The webhook now fails instead, the provider sends it again, and the repeat writes the missing ids.
- **Paddle, Chargebee, Lemon Squeezy and Polar sales were dated when the webhook was handled, not when the sale happened.** A webhook retried after an outage could fall outside the click's token lifetime or the commission period. The provider's own event time is used now (`occurred_at`, `created_at` or `timestamp`), with the current time only when none is sent.
- **Postgres: clean sales were held as fraud.** The conversion-time rule read the hour with `SUBSTR` on a timestamp, which Postgres rejects. Screening turns a rule error into a hold ("screening_error"), so every screened commission was held. The rule now reads the hour from the timestamp as text, and Postgres sessions are pinned to UTC (unless the DSN sets a `timezone`), so times read the same as on SQLite.
- **Postgres: the open fraud count read 0.** The dashboard's "Open fraud verdicts" and "Needs your attention" counted `resolved=0` on a boolean column; Postgres rejected it and the error was ignored. The MCP server's summaries and the weekly digest failed outright, and the digest's top-earner query also had a Postgres `GROUP BY` error. All fixed.
- **About 30 test suites now run on Postgres as well as SQLite** (`AE_TEST_ENGINES=postgres`), instead of SQLite only. Their setup SQL no longer uses SQLite-only forms (`datetime('now', ...)`, `INSERT OR IGNORE`, `X'..'` blobs, `0`/`1` for booleans, `LastInsertId`). `dbtest.At` gives a relative timestamp that works on both engines. The full suite passes on both.
- **Postgres: clicks were never saved.** The click writer's per-day upserts used unqualified column names, so Postgres rejected every batch (`column reference "dc_clicks" is ambiguous`) and dropped each click. A second sale for the same partner on the same day was also left out of the daily sales count. All three upserts now name their table, and new tests run them on both engines. SQLite installs, including every cloud workspace, were not affected.
- **Settings: saving gave no visible answer, and could wipe what you typed.** Every Save now reads "Saving…", then shows "✓ Saved …" (or what's wrong) right next to the button; editing again shows "Unsaved changes". A background refresh (for example after saving the commission) no longer overwrites fields with unsaved or failed edits. The public brand is no longer cached for 60 seconds, so a renamed program shows on the next load.
- **A frozen partner was still paid.** Fraud freezes (and now manual pauses) stopped sign-in and new credit, but approved commissions still went into the next payout. Payout runs now skip paused or removed partners, and the payout gate refuses to pay a payout staged before the pause (it stays waiting, payable again once resumed). Nothing they earned is lost.
- **Postgres: the analytics rollup failed every tick** with `column reference "clicks" is ambiguous`, so daily click counts stopped updating. The upsert now names `daily_agg.clicks`; a test runs it on both engines.
- **Admin screen: tables with a long unbroken reason pushed the Uphold button out of view.** Long reasons now wrap.
- **Admin screen: payout dry run listed bare affiliate ids.** It now shows each affiliate's email with the id; Release/Uphold stay on one line; amounts awaiting approval get thousands separators.
- **Admin screen: Payout run returned "invalid or missing API key".** The request helper spread its options after setting headers, so any call that set Content-Type lost its Authorization header.
- **Paddle: a non-text `custom_data` value failed the webhook on every retry**, so the sale never credited. Numbers and booleans are now read as text; objects and nulls are ignored.
- **Paddle: commission is on the tax-exclusive total** (`total - tax`), matching Stripe's `total_excluding_tax`. Refund adjustments are measured the same way, so a full refund claws the full commission. Blocks without a tax figure fall back to `grand_total` as before.
- **Upgraded SQLite installs never got `campaigns.commission_months`**, so every commission (and the admin campaign list) failed on them after the per-program commission period shipped. A multi-statement migration stopped at its first "duplicate column" and skipped the ADD COLUMN after it. The chain now drops ADD COLUMN statements whose column already exists before running each SQLite file, and `TestSQLiteUpgradeAddsEveryColumn` drops every added column and checks the upgrade restores them all. Stripe retries failed webhooks for 3 days, so those sales credit once this is deployed.
- **Sales from a second program were credited under program 1.** Token, IP-fallback and customer-binding sales took program 1's rate, hold days and commission months, whatever link was clicked (only coupons carried their program). The resolver now reads the click's campaign, and customer bindings store theirs (`customers.campaign_id`, migration `custcampaign`), so renewals stay in the program they started in. Existing bindings read as program 1, which is what they were credited under.
- **A failed ledger write during maturation or a fraud uphold could leave a commission out of step with its money.** Both paths changed the commission's status first and posted the journal second; when the post failed they tried to put the status back, but the status guard rejects `approved -> pending` and `cancelled -> pending`, so the revert never worked. Maturation left the commission `approved` with its money still in HOLD (a later uphold then clawed the affiliate's payable instead); uphold left it `cancelled` with its hold resolved and nothing clawed. Both now post the journal first and change the status after, so a failed post changes nothing and the next run finishes it; if the status changed underneath (another process), an inverse journal puts the money back. Affects releases since v0.2.5, only when a ledger write fails mid-operation. Found by the night-build audit; regression tests fail on the old code.
- **A settle key held by another journal no longer loops a payout forever.** Approve marked it `requested` again on every run; it is now `failed` with the reason in `attention`, for the operator to reconcile. Other failures keep any existing `attention` note.
- **Import undo deleted referral codes that were in use.** A code the batch attached to an affiliate who already existed was removed without checking traffic, breaking live links. Clicks now record the code they came through (`clicks.ref_code`, migration `clickcode_*.sql`), and undo refuses, naming the code, when any code the batch created (on a new or an existing affiliate) has clicks or attributions since the import.
- **The PayPal and Wise files could pay what Approve would refuse, and pay it twice.** The export listed every `requested` payout: ones with an open fraud hold, a pending or rejected tax form, or a commission no longer approved, and payouts of every method in both files. Paying a file and then failing Approve left money paid but still payable, and a restaged payout's commissions could go into a second file. Now each file lists only payouts whose method is its rail and that pass the same gate Approve runs, and claims them under the money lock (`exported_at`, `export_batch`; write-once, guard `trg_payout_export_once`), so a payout is never in two files. Approve re-checks the gate on an exported payout, never runs a rail for it and never restages it: if the gate blocks it, it stays `requested` with `attention` set for the operator. New migration `payoutexport_*.sql`.
- **Re-running an import minted new referral codes** (`janeslink-3`, `-4`...) for affiliates who already held theirs. A code the affiliate already owns is no longer a clash.
- **`coupon_hijack` never fired on real sales.** Billing adapters resolve the attribution ladder themselves and passed only the affiliate, so every credit was stored as `explicit` and the rule, which counts coupon-credited sales, never saw one. The rung (token, coupon, customer) now travels with the event.

### Security
- **Cloud: a removed teammate kept admin access.** Teammates could show the workspace API key and mint dashboard keys, and removing them only signed them out. Now removing a teammate who joined replaces each workspace's API key and revokes every dashboard key at once. Update integrations with the new key (Settings, Show API key).
- **Cloud: keys, billing connections, webhook secrets, settings and the domain are owner-only.** Teammates open dashboards and can see the settings page, but showing or replacing the API key, saving settings, connecting or disconnecting Stripe, Paddle or Lemon Squeezy, and adding, checking or removing a domain answer "Only the account owner can do that."

## [v0.2.11] — 2026-09-25

Usage-path money release: commissions settled from metered usage were permanently stranded. Present since usage settlement shipped (pre-v0.1.0), so every released binary is affected. Also carries the MLM pairing CAS fix recorded below (no production caller could have double-paid, but the fix ships in this tag).

### Fixed
- **Usage-settled commissions were stuck `pending` forever — their money stranded in HOLD.** `SettleDay` inserted commissions with `matures_at = NULL`, but the maturation worker selects `matures_at <= now`, and NULL never compares true on either engine. Every commission ever created by a usage settlement (the metered/AI-SaaS path) sat `pending` indefinitely; the affiliate was never paid and the operator's HOLD liability never released (FR-16 broken end-to-end on this path). Purchase-path commissions were unaffected — `ProcessPurchase` always stamped a NET-terms deadline. Fixed by mirroring the purchase path: settled rows now carry `now + net_terms_days` (program-configured, default 30). **Heal on upgrade:** existing stuck rows are re-dated automatically — the `serve`, `migrate`, and every CLI path re-apply the idempotent migration chain, which now sets `matures_at = created_at + NET terms` for still-NULL pending usage-origin rows (matched via the rate snapshot's `origin` marker; purchase-origin rows untouched). Those commissions then mature on their normal schedule. Verified red pre-fix and green post-fix on SQLite and PostgreSQL 18.6, with regression tests covering both the settle→mature→payable loop and the migration heal.
- **MLM pairing: a lost CAS could report a payout that never happened (PG only).** `SettlePairs` computed new pairs from a read of `pairs_paid`, then CAS-updated `WHERE … AND pairs_paid = ?` without checking `RowsAffected`. On PostgreSQL READ COMMITTED, when two settles race, the loser's UPDATE blocks on the winner's row lock, re-evaluates the predicate after the winner commits, and matches **zero rows — with `err=nil`**. The loser then returned `(pairs, payout)` as if it had paid; any caller posting the payout from the return value would pay twice. On SQLite (`_txlock=immediate`) the loser fails at `BEGIN` with BUSY and retries into a fresh read, which is why this never fired on the SQLite leg. Caught by the 2026-09-25 nightly (flake-hunt shard 3, full PG suite); reproduced deterministically with a lock-orchestrated regression (held row lock → CAS blocks → winner commits → CAS re-evaluates and matches 0), verified red pre-fix and green post-fix. The CAS is now checked: `RowsAffected == 0` returns `(0, 0, nil)` — the row already reflects the winner's payout, and volume arriving after the read is picked up by the next settle. No production caller posts from `SettlePairs`' return value today (engine API + attack suite only), so no released binary could have double-paid. Same-class audit of every money-path CAS (commissions mature/clawback, fraud uphold, payouts runner): all were already checked — this was the last unchecked one.

## [v0.2.10] — 2026-09-25

Restore data-loss release: two data-destroying bugs (present since `restore` shipped in v0.2.2) plus the durability hardening that makes the restore protocol actually crash-safe. Found by the 2026-09-24 restore drill, each probed for real before fixing.

### Fixed
- **`restore --force` could silently replay a foreign WAL onto the restored db.** Restore removed the stale `-wal`/`-shm` sidecars only on the swap path, not on `--force` (live db lost) — precisely the crash scenario most likely to leave a stale WAL next to the db path. Probed for real: a foreign WAL left beside the restored file is replayed onto it silently (SQLite recovers frames when the page size matches and the salt/checksum align), so the engine reads the OLD database's post-backup state while the operator believes they are on the backup — `integrity_check` reports "ok" the whole time. Sidecar removal now runs on every path; a failed removal aborts.
- **`restore` over a live db could destroy the pre-restore state it claimed to preserve.** In WAL mode the live main file can be a near-empty shell while the entire database sits in `-wal` (measured: 4096-byte main vs 1.7MB wal on a quiet install; auto-checkpoint only fires at ~1000 dirty pages). The swap path renamed the shell away and then deleted the sidecars — the `.pre-restore-*` rollback copy held nothing. Restore now TRUNCATE-checkpoints the live db first so the rollback copy is self-contained; if the checkpoint cannot run (locked or corrupt live db — exactly why operators restore), the sidecars are preserved beside the rollback copy as a forensic pair instead of being deleted.
- **Restore/backup durability: the crash-safety the protocol header promised is now real.** (1) The staged copy was promoted by a metadata-only rename without ever fsyncing its pages — a power cut after the promote could leave the *live money database* truncated or empty, during disaster recovery of all times; the staged copy is now fsynced before the rename. (2) Neither the promote rename nor the sidecar removals were made durable — fsyncing the containing directory after the swap flushes them. (3) The same class in `backup`: SQLite fsyncs a `VACUUM INTO` output's pages on commit, but the new file's *directory entry* was never fsynced, so a power cut could corrupt the very artifact disaster recovery depends on. Directory-fsync failure degrades to a loud warning (some filesystems do not support it), never a silent gap.

### Changed
- **CI runners pinned to `ubuntu-24.04`.** GitHub migrates the `ubuntu-latest` label to Ubuntu 26 on 2026-10-19 (actions/runner-images#14748); all four workflows (ci, nightly, release, coverage) rode `ubuntu-latest`, so that flip would have silently changed the OS under CI, the nightly flake-hunt, and the release pipeline with no commit involved. Pinning is a no-op today (`ubuntu-latest` currently resolves to 24.04) and makes the eventual Ubuntu-26 move a deliberate, tested change.
